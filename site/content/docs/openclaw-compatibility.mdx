---
title: OpenClaw compatibility
description: Which OpenClaw versions this release line supports, and why 2.0 is refused.
---

| OpenClaw version | Support |
|---|---|
| `2026.7.1-2` | **Recommended** |
| `2026.4.5` – `2026.7.1-2` | Supported |
| `< 2026.4.5` | Not supported — different config schemas |
| `>= 2026.8.1` | **Not supported on clawops 1.x** — use clawops 2.x |

`spec/openclaw-versions.yaml` is the canonical matrix, and since v1.7.2 it is **enforced**:
`doctor`, `plan`, `up` and `apply` refuse a version outside the range.

## Why 2.0 is refused

OpenClaw `2026.8.1` changed the container runtime contract. Verified against a real deployment:

- **State moved into SQLite** under a state directory this line does not mount, so every container
  replacement discards sessions, transcripts and credentials.
- **Config moved to a writable path.** The file this line mounts is read by nothing.
- **Model providers became install-gated plugins.** A configured but uninstalled provider prevents
  the gateway from starting at all.

Deploying it produces a gateway that crash-loops with exit 78. Refusing is the better failure.

## Moving tags

`latest` and `stable` both point at OpenClaw 2.0 today. clawops resolves a moving tag to a concrete
release **before** range-checking it, and refuses a tag it cannot resolve rather than assuming
compatibility. The default version is a concrete pin.

## Already deployed 2.0?

```bash
clawops doctor --stack <name>
```

reports the version a gateway is actually running, and warns that state may already have been lost —
because with no state volume mounted, every restart discarded it.

## What's coming

Support for the 2.0 line ships in **clawops 2.x**, alongside `clawops migrate` for existing
deployments. The two lines are pinned: clawops `1.x` to OpenClaw `<= 2026.7.1-2`, clawops `2.x` to
`>= 2026.9.1`. The 1.x line is supported until **2027-03-31**.
