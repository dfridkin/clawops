# clawops Threat Model

**Version:** 1.0
**Date:** 2026-05-04
**Owner:** Project author
**Review cadence:** Annually + on major architectural changes

This document explains *why* clawops's security design is what it is. It complements `SECURITY.md` (disclosure process) and `DESIGN_RULES.md` (the rules themselves).

## 1. Assets

What we're protecting:

| Asset | Where it lives | Sensitivity |
|---|---|---|
| **Cloud credentials** | User's environment, cloud CLI config, instance metadata | High — gives full account access |
| **Gateway tokens** | Cloud secret stores (SSM, Secret Manager, Key Vault); systemd EnvironmentFile on the instance | High — gives full OpenClaw control |
| **Channel auth tokens** (Slack, Discord, etc.) | Same as above | Medium — channel-specific impact |
| **Provisioned infrastructure** | Cloud accounts | High — unauthorized destruction or modification = real cost / damage |
| **Pulumi state files** | Cloud blob (S3, GCS, ADLS) | Medium — leakage reveals infra structure but not secrets if encrypted |
| **clawops config** (`~/.clawops/config.json`) | User's home directory | Low — references only, no secrets (R6) |
| **Audit logs** | stderr → wherever the user redirects | Low-Medium — sanitized (R21) |
| **SSH private keys** (auto-generated) | `~/.clawops/keys/` (mode 0600) | High — gives instance shell access |

## 2. Actors

Who's involved and what they can do:

| Actor | Capabilities | Trust level |
|---|---|---|
| **End user (developer/ops)** | Runs clawops CLI, configures credentials, approves plans | Trusted |
| **AI agent (via MCP)** | Calls clawops MCP tools on user's behalf | Semi-trusted (capability-bounded) |
| **CI system** | Runs clawops in non-interactive mode for deploy automation | Trusted (with scoped credentials) |
| **Cloud provider** | Hosts the deployed infrastructure | Trusted (with caveats) |
| **OpenClaw upstream** | Provides the gateway software | Trusted (with version pinning) |
| **Third-party MCP client** | A non-Claude MCP-speaking tool that connects to clawops's standalone MCP server | Untrusted by default |
| **Network attacker** | On-path between client and cloud | Untrusted |
| **Malicious skill author** (OpenClaw skill) | Author of an OpenClaw skill the user installs | Untrusted |
| **Compromised dev machine** | Attacker with local shell as the user | Out-of-scope (game over) |

## 3. Threat Scenarios and Mitigations

### T1: Credentials leak via logs or audit trail

**Scenario:** Cloud credentials, gateway tokens, or channel auth tokens appear in plain text in stderr logs, audit trail entries, or MCP tool argument captures.

**Impact:** High — full account compromise possible.

**Mitigations:**
- R6: credentials never accepted in tool args or stored in clawops config
- ADR 0007: pino redaction patterns strip credentials at the log level
- `spec/errors.yaml` `redaction.patterns` defines the canonical sensitive-key list
- `src/mcp/audit.ts` performs additional sanitization on tool args before audit-logging
- I12 invariant test asserts redaction works
- Test: `tests/logging/redaction.test.ts`, `tests/mcp/audit-sanitization.test.ts`

**Residual risk:** A future contributor adds a new cloud provider with a credential field name not matching the pattern list. **Detection**: ADR 0008 (when written) requires updating `spec/errors.yaml` patterns when adding a provider.

### T2: AI agent invokes destructive tool without consent

**Scenario:** A Claude Code session, Cursor, or third-party MCP client invokes `clawops_destroy` due to misunderstanding user intent or prompt injection.

**Impact:** High — unintended infra destruction.

**Mitigations:**
- R19: destructive tools call `ctx.elicit()` showing the resource diff before executing
- R18: `--read-only` and `--no-destructive` modes filter destructive tools at registration (they don't appear in `tools/list`)
- R10: `destructiveHint: true` ensures conformant clients show extra confirmation
- Maker pattern: agents are encouraged to use `clawops_plan` + `clawops_apply` rather than direct `clawops_up` for high-stakes ops
- Audit log captures every tool invocation with attribution

**Residual risk:** An MCP client that doesn't respect `destructiveHint` and ignores elicitation. **Detection**: audit log review.

### T3: Plan tampering

**Scenario:** A Maker plan generated by `clawops plan` is modified between generation and `apply` to inject malicious resources or change resource attributes.

**Impact:** High — silent compromise of deployed infrastructure.

**Mitigations:**
- Plans are JSON conforming to `spec/deploy-plan.schema.json` — any malformed plan is rejected at apply time
- Plans embed `metadata.generatedAt` and `metadata.generator` so post-hoc review can spot anomalies
- Future: add an HMAC signature in `metadata.signature` keyed off a per-stack secret (deferred to v1.1; tracked in ADR 00XX)
- The agent flow encourages immediate apply after plan generation

**Residual risk:** Without signature verification (v1 scope), local tampering is detectable only by review. **Mitigation in v1.1+:** signed plans.

### T4: State backend compromise

**Scenario:** Pulumi state files in the cloud blob are read or modified by an unauthorized party.

**Impact:** Medium-High — read leaks infra structure (resource IDs, IPs); write enables impersonating a deploy.

**Mitigations:**
- State backend uses cloud-native IAM (S3 bucket policies, GCS IAM, Azure RBAC)
- Pulumi state is encrypted at rest by all major cloud providers' default settings
- clawops uses the user's existing cloud credentials (R6); no separate state-backend creds to leak
- `clawops doctor` warns if the state bucket has public-read or overly permissive policies (when implemented in v1.1+)

**Residual risk:** User misconfigures their bucket. **Mitigation:** clawops's `init` wizard warns about common misconfigurations.

### T5: Token forwarding ("confused deputy") in MCP HTTP mode

**Scenario:** A client authenticates to clawops's standalone MCP server with bearer token X. clawops uses token X to call AWS/GCP/Azure on the client's behalf. The client gains capabilities it wouldn't have directly.

**Impact:** High — privilege escalation.

**Mitigations:**
- R20: clawops's MCP server uses its OWN service-account credentials to call cloud APIs
- Client bearer tokens authenticate the client to clawops, never proxy upstream
- This is explicitly prohibited in MCP June 2025 spec; we follow it strictly
- HTTP mode requires OAuth 2.1 resource server posture in production

**Residual risk:** A misconfigured deployment that does forward tokens. **Detection**: code review on every MCP server change; ADR 0009 (when written) reaffirms this.

### T6: Supply chain compromise

**Scenario:** A dependency of clawops (e.g., a Pulumi provider, the MCP SDK, ssh2) is compromised and ships malicious code.

**Impact:** Critical — affects every deployment.

**Mitigations:**
- npm publish with `--provenance` (sigstore-backed) for clawops itself
- Pinned major versions in `package.json` (allow minor/patch); explicit upgrades via PR
- `pnpm audit` in CI on every PR
- Renovate / Dependabot for tracked dependency updates
- Lockfile committed (`pnpm-lock.yaml`)
- Future: SBOM generation per release (CycloneDX format)

**Residual risk:** Zero-day in a transitive dep before detection. **Mitigation:** rapid response process; users can pin to last-known-good version.

### T7: SSH key leakage or reuse

**Scenario:** Auto-generated SSH private key is exfiltrated, or the same key is reused across stacks giving cross-stack access.

**Impact:** High — instance shell access.

**Mitigations:**
- Per-stack SSH keys (default behavior; user can override with `--key-path`)
- Keys stored in `~/.clawops/keys/` with mode 0600
- Keys never transit the network unencrypted
- `clawops doctor` checks key file permissions
- Host key verification (TOFU + `known_hosts`) prevents MITM

**Residual risk:** If `~/.clawops/keys/` is readable (incorrect umask), keys leak to other local users. **Detection**: `clawops doctor`.

### T8: Egress data exfiltration via skills

**Scenario:** A malicious or compromised OpenClaw skill installed by the user uses the OpenClaw runtime to exfiltrate data to attacker-controlled domains.

**Impact:** Medium — depends on data accessible to skills.

**Mitigations:**
- The "secure profile" (`clawops up --profile secure`) wires Tailscale + Envoy + UFW + DNS allowlist for five-layer egress defense (borrowed from schmitthub/openclaw-deploy)
- The `audit-egress` skill produces periodic reports on allowlisted domains
- Default profile relies on the user's vetting of installed skills

**Residual risk:** Default profile has wide egress. **Mitigation:** documentation prominently encourages secure profile for production.

### T9: Cloud quota exhaustion / runaway cost

**Scenario:** A bug, misconfiguration, or malicious agent causes clawops to repeatedly provision resources, exhausting quota and incurring cost.

**Impact:** Medium — financial damage, denial-of-service.

**Mitigations:**
- Pulumi engine prevents duplicate stack creation (idempotent up)
- `clawops up` requires confirmation for new stacks
- Audit log captures every provisioning attempt
- Documentation recommends cloud-side budget alerts

**Residual risk:** clawops doesn't enforce its own rate limits. **Mitigation:** users configure cloud-side budget alerts.

### T10: Stale credentials in CI

**Scenario:** A CI pipeline holds long-lived AWS/GCP/Azure credentials in env vars that are leaked via logs or compromised CI runner.

**Impact:** High — full account access.

**Mitigations:**
- Documentation strongly recommends OIDC-based auth (e.g., GitHub Actions OIDC → IAM role) over long-lived keys
- ADR for the OIDC pattern (borrowed from Yash-Kavaiya/openclaw-bedrock-ec2)
- clawops itself does not create or rotate credentials; user is responsible

**Residual risk:** Out of scope for clawops itself.
