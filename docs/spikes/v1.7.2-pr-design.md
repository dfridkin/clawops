# v1.7.2 — design (parked, pending spike completion)

Agreed scope, four changes on the `1.x` line. Every mechanism below is **verified** on a real host
against both `2026.7.1` and `2026.8.1` (see SP-01/SP-02 notes).

## 1. Version ceiling  *(the time-critical one)*

`spec/openclaw-versions.yaml` → `support.max: "2026.7.1-2"`. Enforce in `doctor`, plan validation,
`up`, `apply` — **refuse, don't warn**. Error names the fix:
*"OpenClaw 2026.8.1+ requires clawops 2.x — see the migration guide."*

**Resolve `latest`/`stable` to a concrete version _before_ the range check.** Checking first and
resolving after is how the unbounded `support.max` slipped through.

## 2. Detect-and-warn on already-deployed 2.x

Gating future operations does nothing for someone who ran `clawops up` with `"latest"` last week.
`doctor --stack` and `status` inspect the **running container's image tag**, report the mismatch, and
say plainly that state may already have been lost on restart. Separate code path; the half that
helps existing users.

## 3. Config delivery — G3

**`clawops config set` has never worked, on either OpenClaw line.** Verified: a config declaring
`gateway.port: 19999` is ignored by both 2026.7.1 and 2026.8.1 — both bind 18789. The mounted
`/app/config.json` is read by nothing.

Fix: `-e OPENCLAW_CONFIG_PATH=/app/config.json`. Verified — both versions then honour the config.

### Four hardening layers

| Layer | Mechanism | Protects against |
|---|---|---|
| Normalise | Write `gateway.port: 18789`; **warn** if we changed it | Config file tells the truth; intent isn't silently discarded |
| Pin | `--port 18789` on argv — **verified to override config on both versions** | Configs we didn't write: hand-edited, or left by an older clawops |
| Parse-guard | Unparseable config → skip `OPENCLAW_CONFIG_PATH` | Fails to today's behavior, never worse |
| Health-gate | Probe `/healthz` on the published port; revert to the prior run command on failure, keep the old unit as `.bak` | Everything unforeseen |

Normalising alone doesn't cover foreign configs; pinning alone leaves the file lying. Take both.

**Why following the config's port instead is out of scope:** 16 files / 19 references hardcode 18789,
including `harden/modules/ufw.ts` and `aws-sg-audit.ts` (would open the wrong port) and `tunnel.ts`
(derives its port from the stack output). Genuinely configurable ports are WO-42 + WO-48 on the 2.x
line.

**Strict-validation hazard does not apply here:** v1.7.2 refuses 2.0 by construction (item 1), so this
patch only ever talks to ≤2026.7.1, which is lenient. Invalid channel configs (G15) land on the 2.x
line under WO-41.
